### Keystore generation

Created `~/.android-keystores/` with `chmod 700`, generated 48-character
alphanumeric passwords (no shell-special chars to avoid Gradle properties
escaping issues), and ran `keytool -genkeypair` directly as PKCS12 (the modern
storetype the JDK 24 keytool recommends). Discovered the hard way that PKCS12
keystores **do not support distinct store and key passwords** — keytool silently
ignored `-keypass` and reused `-storepass`. Documented in ADR-0014.

Keystore properties:

- Path: `~/.android-keystores/roteirizador-pro.jks` (PKCS12 format)
- Alias: `roteirizador-pro`, RSA 4096, SHA384withRSA self-signed
- Validity: 30 years (2026-05-13 → 2056-05-05)
- DN: `CN=Roteirizador Pro, OU=Mobile, O=Elo Vision Digital, L=Sao Paulo, ST=SP, C=BR`
- Cert SHA-256: `D9:C9:61:D6:…:14:31`
- Cert SHA-1: `FD:FD:56:73:…:2D:63`

The cert fingerprint can be re-derived from the .jks at any time via
`openssl pkcs12 -in <file> -nokeys | openssl x509 -fingerprint -sha256` — the
JDK 24 keytool itself has a `java.util.MissingFormatArgumentException` bug
when listing cert details under `LANG=pt_BR` (and `LANG=C` doesn't escape it
either), so openssl is the more reliable display path.

### Two builds + the split-vs-universal decision

First build with `--split-per-abi` produced `app-arm64-v8a-release.apk` (19.3 MB)
and `app-armeabi-v7a-release.apk` (16.8 MB). Verified the arm64 APK via
`apksigner verify --print-certs`:

- V2 scheme: true; v1/v3 false. Sufficient for Android 7.0+; everything
  Brazilian motoboys ship in 2026.
- Cert SHA-256 matches the keystore (`d9c961d6…14431`).
- DN matches (`CN=Roteirizador Pro, …`).
- Key: RSA 4096.

Then realized that per-ABI distribution forces user-facing routing ("which
Android do I have?"), which is exactly the UX motoboys do not want. Rebuilt
**without `--split-per-abi`** to get a single universal APK targeting both
`arm` and `arm64`:

- `app-release.apk` → **34.3 MB** universal binary. ~10% more bytes than the
  split, but one URL, one button, zero device-detection logic.

Updated `build-release-apk.sh` to default to the universal flag, with a
comment explaining the size/simplicity tradeoff. Documented as Option ε in
ADR-0014.

## Decisions Made

1. **PKCS12 keystore type with a single shared password (store == key).**
   The JDK 24 keytool quietly ignores `-keypass` for PKCS12; this is a
   keystore-format limitation, not a misconfiguration. Documented in ADR-0014.
2. **Universal APK (`--target-platform=android-arm,android-arm64` *without*
   `--split-per-abi`).** 34 MB is small in 2026; user-facing ABI routing is
   bad UX. Documented as Option ε in ADR-0014.
3. **Distribute via Vercel's static `public/` directory** rather than Blob
   storage or GitHub Releases. Zero new infrastructure, the file ships in the
   same PR as code.
4. **Gradle release signing falls back to debug signing when `key.properties`
   is absent.** Keeps CI green and lets fresh clones run `flutter build` for
   non-publishing purposes. The risk (someone publishing a debug-signed APK
   by mistake) is mitigated because publishing requires a manual `cp` to
   `apps/landing/public/`.
5. **`v1.0.0+1` as the first public version**, with `versionCode` (`+N`) bumped
   on every published APK even when the semver is unchanged. Recorded in
   ADR-0014's "Versioning convention" section.
6. **`apps/landing/public/roteirizador-pro-v<semver>.apk` is the filename
   convention.** No build-suffix in the filename, so the URL is stable when
   a hotfix bumps just the `versionCode`.
